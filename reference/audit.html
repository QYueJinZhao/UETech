审核标准与维度

范围：18 章正文 + 交互图解 + 自测 + 章节引用的速查库关键结论

判定口径：概念可对应官方文档/公开技术分享；不把经验说法写成引擎事实；图解简化必须标注；自测要考权衡与边界；动手步骤要能在编辑器走通并写清前提。

概念正确性机制描述能否对应官方文档/公开技术分享；有没有把经验说法写成引擎事实。
原理讲透程度是否解释「为什么这样设计」，还是只罗列现象；类比是否会引起误解。
图解质量示意图与真实机制的关系、简化是否标注、参数是否对应机制量。
难度与节奏每屏信息量、前置是否交代、术语是否首次解释、时长估计是否合理。
自测题质量是否只考记忆、有没有考察权衡与边界条件、解析是否讲清「为什么错」。
动手可执行性步骤能否在编辑器走通、预期现象是否写清、有无遗漏插件/项目设置/版本。
术语与一致性同一概念跨章叫法是否统一，与速查库条目是否对得上。

BLOCKER 2 条

BL-01physics · intuition.body / principle[0]已修

问题把破坏瞬间的碰撞对成本写成「近似平方增长」，并把物理成本增长描述为整体快于线性。

为什么是问题物理引擎先用宽相位（空间划分/哈希）剔除绝大多数远距离对，真正昂贵的是同一局部区域内的密集重叠、窄相位与约束求解迭代。写成全局平方会让读者把优化目标放在「减少物体总数」，而不是「降低局部密度、限制碎片数量与寿命」。

改法改写为：全局有宽相位剔除，但同一区域的密集重叠会让候选对与约束快速增长；成本由活跃刚体、局部密度、求解迭代共同决定。

维度：概念正确性

BL-02loading · principle[3] / costs「Game 线程」/ pitfall / quiz[2] / terms「反序列化」已修

问题断言「反序列化与创建对象必须回到 Game 线程，这部分无法完全并行」。

为什么是问题UE5 的异步加载线程可以承担大部分反序列化，并在满足条件时创建部分 UObject；必须回到 Game 线程的是蓝图类构造、组件注册、PostLoad 与部分依赖解析。把全部工作说成必须回主线程，会让读者误以为异步加载没有主线程收益，也会误判卡顿来源。

改法改成「多数反序列化可在异步加载线程完成，蓝图/组件注册/PostLoad 等仍需 Game 线程」，并在代价、误区、自测与术语四处同步修正。

维度：概念正确性
