全局光照：Lumen 为什么贵，什么时候该烘焙

这一章只回答一个问题：间接光到底是「提前算好」还是「每帧重新估」。理解这个差别，Lumen 的成本、延迟、漏光、以及低端平台为什么要烘焙，就都能自己推出来。

01

你会遇到什么问题

雨夜关卡里，你打碎了一盏路灯

美术希望灯光变化立刻影响整条街：碎掉的灯变暗、湿地面反射出新的高光、远处墙面跟着变。你在编辑器里看很漂亮，打包到主机上却掉到 40fps；调低效果后画面发灰，调高又掉帧。更麻烦的是，快速移动光源时，墙面上的光会「追」上来，像慢半拍。

常见症状：
  • 打开 全局光照与反射系统，结合屏幕空间追踪、表面缓存与场景距离场等近似。">Lumen 后 GPU 帧时间明显上升，但不知道贵在哪个通道
  • 光源或发光材质变化时，间接光有可见延迟、噪点或闪烁
  • 低端机/移动端无法承受，团队临时决定「全部改烘焙」，却发现动态物体不响应
  • 薄墙、墙角出现漏光，无法判断是配置问题还是算法近似
02

一句话直觉

把 Lumen 想成一台「每帧重新测光」的相机：它不承认光已经算好，而是持续估计当前场景的间接光。

相机测光需要采样、计算、平滑；Lumen 也需要追踪射线、取表面颜色、再做时域累积。因为它每帧只更新一部分信息，所以「快」和「准」天然冲突：动态场景越剧烈，你越容易看到延迟与噪点。烘焙则相反，它把光提前算死，运行时只查表，稳定便宜，但场景一旦变化就失效。

类比的边界：类比到这里为止：Lumen 不是电影级路径追踪，它大量依赖屏幕空间与表面缓存，屏幕外和薄几何正是它最容易出错的地方。

03

原理图解

Lumen 先为场景维护一份「表面缓存」：记录各表面的材质、法线、位置等信息，作为射线命中时的取色来源。

追踪时优先做屏幕空间追踪——只用当前相机已经渲染出来的像素，成本低、结果准，但屏幕外的物体它根本不知道。

射线离开屏幕或命中失败时，回退到表面缓存/距离场等场景表示，因此薄墙、背面和屏幕外区域最容易出现漏光或错误遮挡。

间接光不是一次算完：结果做时域累积与去噪，每帧更新一部分，所以快速变化会表现为延迟、拖影或噪点。

反射沿用同一套思路：屏幕空间反射 + 回退，所以「反射里看不到屏幕外的东西」是机制性的，不是 bug。

04

关键代价

GPU
追踪、表面缓存更新、去噪与反射都要占 GPU；分辨率与反弹次数是主要放大器。
显存
表面缓存与各种场景表示常驻显存；大世界要按单元管理。
构建时间
不需要烘焙，迭代快；这是相对烘焙最大的收益之一。
美术规范
发光面积、材质粗糙度、薄墙与尺度都会直接影响结果，必须有规范。
团队成本
需要有人能读 ProfileGPU/可视化视图，否则只能靠猜调参数。

条形为相对量级（1–5 档），不对应具体毫秒、兆字节或人力数字。判断取舍时看「哪一项不可接受」，而不是追求每项都低。

06

常见误区

误区 1把 Lumen 当成「开了就正确」的光照，不做材质与发光面积规范。
正确理解Lumen 是估计器：大面积高亮发光材质、过薄墙体、错误尺度都会放大噪点与漏光。先定美术规范，再谈参数。
误区 2所有平台都用同一套 Lumen 配置，低端机只靠降分辨率硬扛。
正确理解先确认目标平台是否在支持范围内，再准备烘焙/简化回退；分辨率不是万能的，追踪与表面缓存成本不会随分辨率等比例下降。
误区 3看到漏光就认定是 Lumen 的 bug，直接改引擎参数。
正确理解先按机制排查：表面缓存是否覆盖该几何、墙体厚度/距离场精度、屏幕空间可见性、发光材质是否过大。多数漏光来自场景与内容，而不是算法本身。
07

动手复现

前提：UE 5.x 项目默认开启 Lumen；硬件光线追踪需在项目设置启用；对比时固定相机、分辨率与画质档位。

01用 Third Person 模板新建项目，在 Project Settings → Rendering 里把 Dynamic Global Illumination 与 Reflection 设为 Lumen。
预期现象：视口出现间接光与反射；移动光源时能观察到光的变化。
02放一个高亮发光材质立方体，旁边放一面很薄的墙；快速移动立方体。
预期现象：墙面光会「追」上来，薄墙背面可能出现漏光——这是屏幕空间 + 缓存的机制表现。
03打开 stat gpu（或 ProfileGPU），记录 GI/反射相关通道在总 GPU 时间中的占比。
预期现象：能指出成本主要来自哪个通道，而不是只知道「GPU 很高」。
04把 Dynamic Global Illumination 切到 None 或改用烘焙预览，构建一次光照后对比同一场景。
预期现象：静态场景画质接近、运行时更便宜；但移动光源/动态物体不再影响间接光。
05在 Scalability 或后处理里降低 GI 质量档，记录帧时间与画质损失。
预期现象：得到一个可回退的档位，而不是只有「开/关」两个极端。

步骤在编辑器内 5 步以内可复现；预期现象用来自检机制是否成立，不要求截图一致。

08

自测

1. 为什么 Lumen 在光源快速变化时会出现短暂延迟、拖影或噪点？
解析：因为间接光不是一次收敛，而是依赖时域累积与逐帧更新：每帧只补充一部分采样，再靠去噪与历史帧平滑。变化越剧烈，历史信息越不匹配，就越容易看到延迟与噪点。
方案：Lumen 动态 GI vs 烘焙光照问题：昼夜循环下 GI 与阴影不连贯
2. 屏幕空间追踪的固有缺陷是什么？它会怎样表现为画面问题？
解析：它只能使用当前相机已经渲染出的像素，屏幕外、被遮挡或薄几何的信息缺失，必须回退到表面缓存/距离场。表现就是屏幕外物体不贡献间接光、薄墙漏光、反射里看不到画面外的东西。
问题：Lumen 漏光、噪点与闪烁方案：Lumen 动态 GI vs 烘焙光照
3. 什么情况下应该优先选择烘焙，而不是 Lumen？
解析：场景基本静态、目标平台较弱、需要稳定可预测的运行时成本、且美术迭代不频繁时。烘焙把成本移到离线构建，运行时只采样；代价是动态光源/破坏不响应。
方案：Lumen 动态 GI vs 烘焙光照问题：烘焙 Lightmap 接缝与光照不一致
