渲染管线：一帧里到底发生了什么

先不讨论 Lumen、Nanite 这些名字。这一章只建立一条时间线：Game 线程准备数据、Render 线程翻译命令、GPU 执行并呈现。看懂这条线，后面所有「为什么卡」的问题才有坐标。

01

你会遇到什么问题

加了一个半透明特效，帧率直接腰斩

主场景本来 60fps，美术加了一层雾和几个半透明特效后掉到 35fps。你试着降低材质精度、关掉阴影，效果都不明显；把分辨率降一半，帧率回来一些，但画面糊得不能看。团队里有人说「GPU 不行」，有人说是「CPU 太慢」，可是没人能指出具体是哪一段。

常见症状：
  • 不知道瓶颈在 Game 线程、Render 线程还是 GPU
  • 加特效/加光源就掉帧，但删掉任意一个都恢复不满
  • 降低分辨率有效，降低画质效果不明显
  • 编辑器里流畅，打包后变慢（或反过来）
02

一句话直觉

把一帧想成一条装配线：Game 线程备料，Render 线程把料翻译成 GPU 能执行的命令，GPU 才是真正干活的车间。

装配线可以重叠：这一帧的 GPU 在渲染时，下一帧的 Game 线程已经在准备。所以帧时间不是三者相加，而是取最慢的一环。半透明特效主要压 GPU 的填充与带宽；Actor 太多、Tick 太重主要压 Game 线程；两者都会让你看到「掉帧」，但解法完全相反。

类比的边界：装配线类比不体现同步点：渲染线程要等 Game 线程的数据、GPU 要等命令提交，真正的并行程度取决于这些等待与缓冲。

03

原理图解

Game 线程每帧执行 Actor Tick、蓝图、动画、物理与游戏逻辑，产出这一帧要渲染的场景状态。

Render 线程把场景状态翻译成渲染命令（可见性、材质、绘制调用），再通过 RHI 提交给 GPU；它和 Game 线程可以并行，但受同步点约束。

GPU 执行绘制与计算：顶点处理、光栅化、像素着色、后处理，最后呈现到屏幕；填充率、带宽与着色复杂度是主要成本。

CPU 与 GPU 通过若干帧的缓冲重叠工作，所以「CPU 一帧 20ms、GPU 一帧 10ms」时整体仍可能接近 20ms，而不是 30ms。

定位顺序是固定的：先看哪一环最高（stat unit），再看该环内部的热点（ProfileGPU / Insights / 逐项开关），最后才决定优化手段。

展开：再深一层的机制与边界
为什么不能只盯一个数字：同一帧里 CPU 可能被同步点阻塞（等待 GPU 或等待渲染线程），GPU 也可能在等命令。把「线程时间」和「墙钟帧时间」混为一谈，就会得出错误的优化方向。真正的验证要在目标平台、目标画质、固定场景下重复测量。
04

关键代价

GPU
分辨率、半透明 overdraw、后处理与光照是主要放大器。
CPU
Actor/ Tick 数量、蓝图、动画与物理都会推高 Game 线程。
内存 / 带宽
纹理、RT 与流送影响显存与带宽，移动端尤其敏感。
美术规范
半透明层数、材质指令数、光源数量需要规范，否则优化永远追不上新增内容。
团队协作
需要统一观测口径与固定测试场景，否则各说各话。

条形为相对量级（1–5 档），不对应具体毫秒、兆字节或人力数字。判断取舍时看「哪一项不可接受」，而不是追求每项都低。

06

常见误区

误区 1用平均 FPS 判断性能，忽略 1% low 与单帧尖峰。
正确理解玩家感知的是卡顿帧。记录帧时间分布与尖峰，固定场景重复测量；平均 60fps 也可能每 10 秒卡一次。
误区 2一掉帧就降分辨率，认为所有问题都在 GPU。
正确理解先看 stat unit：Game/Draw/GPU 谁高。CPU 瓶颈降分辨率几乎无效，反而白白损失画质。
误区 3在编辑器里调好就认为打包后没问题。
正确理解编辑器有额外开销、热缓存与不同线程模型；必须在目标平台打包构建上验证，并用固定场景对比。
07

动手复现

前提：UE 5.x；PIE 可看趋势，代表性数值应在打包构建/Standalone 固定机位取；同时开 stat unit 与 stat fps。

01打开任意模板关卡，控制台执行 stat unit，记录 Game / Draw / GPU 三个数。
预期现象：能指出当前帧由哪一环主导，而不是只说「卡」。
02执行 stat fps 与 stat scenerendering，观察 Draw call、可见 Actor 与三角形数量。
预期现象：对「场景复杂度」有一个可量化的起点。
03在场景里叠加几层半透明粒子/雾，再看 stat unit 与 ProfileGPU。
预期现象：GPU 通道上升明显，CPU 变化较小——验证填充率/带宽假设。
04把分辨率缩放调到 50%，对比同一位置的帧时间。
预期现象：若 GPU 主导则明显改善；若 Game 线程主导则改善有限。
05在 Project Settings 里切换 Forward/Deferred（若平台允许），对比多光源场景。
预期现象：看到两条路径在多光源与带宽上的不同取舍，而不是「谁更高级」。

步骤在编辑器内 5 步以内可复现；预期现象用来自检机制是否成立，不要求截图一致。

08

自测

1. CPU 一帧 20ms、GPU 一帧 10ms，为什么整体帧时间通常不是 30ms？
解析：因为 CPU 与 GPU 通过多帧缓冲重叠工作：GPU 渲染第 N 帧时，CPU 已在准备第 N+1 帧。整体接近较慢的一环（约 20ms），前提是没有同步点把两者串行化。
问题：渲染 Pass 顺序与带宽浪费难以定位面试题：RTS 战争迷雾如何同时保证逻辑正确、渲染平滑和信息安全？
2. 半透明特效为什么比不透明物体更容易打爆 GPU？
解析：不透明物体可以靠深度测试/ Early-Z 剔除被遮挡像素；半透明通常要混合、不能随意剔除，层数叠加会重复着色并增加带宽，overdraw 直接变成成本。
方案：TBDR、带宽与填充率：过度绘制治理问题：Draw call 与 overdraw 把 GPU 压到帧率腰斩
3. 看到掉帧时，第一件事应该做什么？
解析：先用 stat unit / ProfileGPU 定位是 Game、Render 还是 GPU 主导，再在目标平台固定场景下测量；没有定位就优化，等于随机改参数。
