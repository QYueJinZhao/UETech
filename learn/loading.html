资源加载：为什么打开背包会卡一下

这一章只讲一件事：资产不是「打开就有」，它要被找到、读出来、解压、反序列化、再创建成对象。任何一步放到 Game 线程上同步做，玩家就会看到卡顿。

01

你会遇到什么问题

第一次打开背包，帧率掉到个位数

背包界面在编辑器里一点就开，打包后第一次打开会卡将近一秒，第二次就正常了。传送、切场景、第一次放技能也都有类似的「首次卡顿」。你把界面做简单一点，卡顿只减轻一点；把资产压小，卡顿时间变短但仍然存在。

常见症状：
  • 首次触发才卡，重复触发不卡（缓存掩盖了问题）
  • 低端机/机械硬盘/网络盘上卡顿明显放大
  • 卡顿发生在 Game 线程，ProfileGPU 看不出异常
  • 改用「预加载」后卡顿转移到了另一个时点，而不是消失
02

一句话直觉

加载像把仓库里的货搬到前台：搬运本身要占人手、走通道、拆包装，不会因为你看不见仓库就免费。

「找到资产 → 从磁盘/网络读字节 → 解压 → 反序列化成 UObject → 创建依赖对象」是一条流水线。同步加载把整条流水线塞进当前帧，帧时间就被拉长；异步加载把流水线摊到多帧与后台线程，但总工作量没变，只是不再一次性砸在玩家头上。

类比的边界：类比到这里为止：真实加载还有缓存、依赖图、包文件索引与 IO 调度，命中缓存时确实几乎免费——这正是「第二次不卡」的原因，也是测试最容易骗人的地方。

03

原理图解

加载先要「找到」资产：通过引用或 Asset Manager 的 Primary Asset 规则定位包文件与导出表，这一步本身有 CPU 成本。

然后是 IO 与解压：从 Pak/IoStore 读出字节并解压，可放到后台线程与异步 IO；网络盘、机械盘与低端设备上这一段最先成为瓶颈。

反序列化与对象创建大多可以在异步加载线程完成（资产类型不同，允许的并行度不同）；但蓝图类构造、组件注册、PostLoad 与部分依赖解析仍要回到 Game 线程。异步能削掉 IO/解压和大部分反序列化，却削不掉所有主线程尖峰。

同步 LoadObject 会阻塞调用线程直到整条流水线完成；异步加载把工作拆成请求 + 回调，让帧继续跑，但对象在回调前不可用。

预加载不是消除成本，而是把成本提前到可控时点（加载画面、过场、流送边界），所以必须同时管住内存峰值。

展开：再深一层的机制与边界
为什么「第二次就快」不能当作修好了：第一次之后资产已在内存或 OS 文件缓存里，第二次省掉的是 IO 与解压，反序列化与创建仍然发生。要验证真实体验，必须在「冷启动 + 首次触发」的条件下测。
04

关键代价

内存
预加载与缓存会把资产常驻内存；加载得越早越顺，占的内存越多。
IO / 解压
包体压缩率越高，解压 CPU 越高；不压缩则 IO 字节更多，需要按平台权衡。
Game 线程
多数反序列化可在异步加载线程完成；蓝图/组件注册/PostLoad 等仍需 Game 线程，主线程尖峰无法完全消除。
包体
拆包与分包会改变加载粒度，也改变首包体积与补丁大小。
美术规范
资产粒度、贴图尺寸、依赖深度直接决定单次加载的工作量。

条形为相对量级（1–5 档），不对应具体毫秒、兆字节或人力数字。判断取舍时看「哪一项不可接受」，而不是追求每项都低。

06

常见误区

误区 1在编辑器里点一次很快，就认为加载没问题。
正确理解编辑器有热缓存与更快的存储。必须在打包构建、冷启动、首次触发的条件下测，才看得到真实尖峰。
误区 2把所有资产都改成异步加载，就以为卡顿消失了。
正确理解异步不只挪走 IO 与解压：多数反序列化可在异步加载线程完成，但蓝图构造、组件注册与 PostLoad 仍要 Game 线程；并发请求过多时主线程仍会出现尖峰。
误区 3用预加载解决一切，不看内存预算。
正确理解预加载是把卡顿换成内存。先确认目标设备的内存上限与流送预算，再决定预加载范围；否则会从「卡顿」变成「闪退」。
07

动手复现

前提：UE 5.x；在打包构建或 Standalone 冷启动下测，PIE 有热缓存；用 stat unit 与加载日志对照。

01在打包构建里打开 stat unit 与 stat loading（若版本提供），首次打开一个含大量资产的界面。
预期现象：能看到 Game 线程出现明显尖峰，而 GPU 基本不变。
02用 Unreal Insights 或 Profiling 记录这一次加载，展开调用栈。
预期现象：能指出时间花在 IO/解压还是反序列化/创建对象。
03把该界面改为异步加载，并在加载期间显示占位。
预期现象：单帧尖峰被摊平，但总时长不变，且出现「加载中」状态。
04在进入界面之前做一次预加载（或预热一次隐藏界面）。
预期现象：进入时几乎无卡顿，同时观察内存曲线抬高。
05在低端机或限速存储上重复同一组对比。
预期现象：IO 瓶颈被放大，帮助你判断该优先压缩包体还是拆分资产。

步骤在编辑器内 5 步以内可复现；预期现象用来自检机制是否成立，不要求截图一致。

08

自测

1. 为什么同一个界面「第二次打开」就不卡了？
解析：第一次已经把资产读入内存或 OS 文件缓存，第二次省掉了 IO 与解压；但反序列化与对象创建仍会发生。所以「第二次不卡」不能证明加载路径健康。
方案：同步 vs 异步加载与 StreamableManager问题：首次打开技能/背包界面卡顿
2. 异步加载为什么不能完全消除卡顿？
解析：因为蓝图类构造、组件注册、PostLoad 与部分依赖解析必须回到 Game 线程；异步加载线程能承担 IO、解压和多数反序列化，但削不掉所有主线程工作。请求过多时仍会形成尖峰。
问题：软引用加载失败或对象被回收后无兜底方案：预加载、预缓存与加载画面
3. 预加载的主要代价是什么？什么时候值得付？
解析：代价是内存常驻与「预加载了但没用上」的浪费。当下一步动作可预测（进副本、打开固定界面、跨流送边界）且内存预算允许时值得。
