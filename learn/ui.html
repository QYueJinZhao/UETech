UI 性能：界面不复杂，为什么也掉帧

UI 的成本有两份：一份是每帧重建与布局的 CPU，一份是半透明叠加的 GPU。两者都跟「有多少控件在动」有关，而不是「界面看起来多复杂」。

01

你会遇到什么问题

打开背包，帧率从 60 掉到 45

背包是一个网格列表，滚动时明显掉帧；关闭背包就恢复。界面美术并不复杂，但每帧都有大量控件在更新位置、绑定数据与刷新文本。

常见症状：
  • 打开/滚动界面时 CPU 或 GPU 上升，关闭即恢复
  • 控件越多越慢，尤其是列表与文本
  • 半透明面板叠加后掉帧，尤其在移动端
  • 数据绑定每帧刷新，即使数值没变
02

一句话直觉

UI 像每帧重排一次版面：只要有控件在动，排版与绘制就要重做；不动的部分本可以不动。

UMG/Slate 每帧要做布局、构建绘制列表与提交；数据绑定若没有变化检测，就会每帧触发无意义的重建。GPU 侧则是半透明面板的 overdraw：层数越多、覆盖面积越大，混合成本越高。所以 UI 优化的核心是「减少每帧真正需要变化的部分」。

类比的边界：重排版面类比不体现「失效与缓存」：真实实现有失效标记与缓存，做得好的话静态部分几乎零成本——问题往往出在「让一切都失效了」。

03

原理图解

UI 的开销分两部分：CPU 侧的失效重排/构建/绑定，GPU 侧的半透明绘制与 overdraw；只有被标记失效或数值变化的控件才重做，静态部分可复用。

控件数量与「是否变化」决定 CPU 成本：静态控件可被缓存，频繁变化的控件会不断触发重建。

数据绑定若每帧轮询而不做变化检测，会让「没变的东西」也重新计算，这是最常见的隐形开销。

半透明面板会叠加混合，层数越多、面积越大越贵；移动端带宽有限，尤其明显。

列表类界面应做虚拟化/复用：只创建可见项，滚动时复用控件，而不是整表重建。

06

常见误区

误区 1界面看起来简单，就认为 UI 不会成为瓶颈。
正确理解成本取决于控件数量与变化频率，而不是视觉复杂度。长列表、每帧绑定与半透明叠加都可能很贵。
误区 2让数据绑定每帧轮询，靠「反正数值没变」自我安慰。
正确理解没有变化检测的轮询会每帧触发重建。应使用事件/脏标记，只在值真的变化时更新。
误区 3在移动端堆叠多层半透明面板做「高级感」。
正确理解半透明叠加直接转成 overdraw 与带宽。移动端应减少层数与覆盖面积，必要时用不透明替代。
07

动手复现

前提：UE 5.x；用 stat ui / stat slate（版本不同命令名可能不同）；移动端 overdraw 需真机或 GPU 抓帧。

01打开一个长列表界面并滚动，记录 stat unit 与 UI 相关统计。
预期现象：CPU 或 GPU 明显上升，关闭后恢复。
02把列表改为只创建可见项（虚拟化/复用）。
预期现象：滚动时 CPU 显著下降，条目总数不再影响每帧成本。
03检查数据绑定是否每帧刷新，改为变化时更新。
预期现象：静止界面的 CPU 降到接近零。
04叠加半透明面板并观察 GPU 时间。
预期现象：层数增加时 GPU 上升，验证 overdraw 成本。
05在移动端重复同一组测试。
预期现象：带宽限制让差异更明显，得到分档依据。

步骤在编辑器内 5 步以内可复现；预期现象用来自检机制是否成立，不要求截图一致。

08

自测

1. 为什么「界面简单」不代表 UI 性能好？
解析：UI 成本取决于控件数量、变化频率与半透明层数，而不是视觉复杂度。长列表每帧重建、绑定轮询与多层透明都会很贵。
方案：UI 性能：UMG/Slate 的绘制与更新成本问题：背包/长列表滚动卡顿
2. 虚拟化列表解决了什么问题？
解析：它只创建与更新可见项，滚动时复用控件，使每帧成本与「可见数量」相关，而不是与「总条目数」相关。
方案：背包/复杂 UI：UMG 优化与数据虚拟化问题：UI 每帧失效重绘导致 CPU/GPU 浪费
3. 数据绑定为什么要做变化检测？
解析：没有变化检测的轮询会让没变的控件也触发重建，造成持续的 CPU 开销；用事件或脏标记可以只在值变化时更新。
