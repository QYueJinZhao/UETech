性能优化：先定位，再谈预算

性能不是「感觉慢」，而是一笔可以分配的预算：每帧有多少毫秒，Game、Render、GPU 各花多少，谁超了。这一章建立一套可复现的定位与回归方法。

01

你会遇到什么问题

这次更新后，帧率掉了 15 帧，但没人说得清为什么

版本上线前一周，测试反馈「战斗里偶尔卡」。你打开编辑器看，帧率忽高忽低；关掉特效好一点，加回来又掉。每个人都在改自己负责的部分，没人有一份固定场景的基线，也没人能在合并前发现退化。

常见症状：
  • 同一台机器、同一关卡，两次测量结果差很多
  • 只知道「掉帧」，不知道是 Game、Render 还是 GPU
  • 优化后无法证明真的变快（没有基线）
  • 问题在打包/联机/真机上才出现，编辑器复现不了
02

一句话直觉

把每帧当成一笔固定预算：60fps 只有约 16.7ms，谁花超了，帧就没了。

优化的第一步不是「改」，而是「量」：先知道总预算是多少、每个线程花了多少、哪个通道最高。第二步才是针对最高的一项做取舍。没有测量就没有优化，只有碰运气。

类比的边界：预算不是越低越好：画质、玩法与团队产能也在预算里。性能工作的目标是「可解释、可回归」，不是把所有数字压到最小。

03

原理图解

先定目标：目标帧率决定每帧预算（例如 60fps ≈ 16.7ms），并明确「平均」与「1% low / 尖峰」两个口径。

再分线程：stat unit 给出 Game、Draw（Render 线程）与 GPU 的时间；最高的一项就是当前瓶颈。

再看通道：ProfileGPU / Insights 把 GPU 拆成 Base Pass、光照、后处理、UI 等；CPU 侧看 Tick、动画、物理、蓝图与网络。

优化必须可复现：固定关卡、固定机位、固定画质、固定设备，重复采样，记录分位数而不是单次数字。

最后做回归：把关键场景接入自动化/性能门槛，合并前对比基线，超过阈值就阻断，而不是等到上线前才发现。

展开：再深一层的机制与边界
为什么「平均值」会骗人：卡顿往往来自少数长帧（PSO 首次编译、GC、流送、加载），平均帧率会被大量正常帧稀释。要同时看帧时间曲线、1% low 与尖峰位置，才能判断是持续超预算还是周期性事件。
04

关键代价

开发时间
固定场景、基线、自动化都要持续投入，且需要跨职能协作。
画质
降分辨率、降阴影、降后处理都会直接损失观感，需要分级而不是一刀切。
内存 / 带宽
有些优化用内存换时间（缓存、预计算），要同时看峰值。
团队习惯
没有统一观测口径，数据就不可比；性能必须成为提交规范的一部分。
平台差异
PC、主机、移动端的瓶颈完全不同，不能拿一个平台的数据下结论。

条形为相对量级（1–5 档），不对应具体毫秒、兆字节或人力数字。判断取舍时看「哪一项不可接受」，而不是追求每项都低。

06

常见误区

误区 1只看平均帧率，不看 1% low 与长帧。
正确理解卡顿由少数长帧决定。记录帧时间分布与尖峰，定位周期性事件（GC、流送、PSO），否则会优化错方向。
误区 2在编辑器里测完就下结论。
正确理解编辑器线程模型、缓存与打包版本不同；必须在目标平台打包构建、固定画质下复测。
误区 3没有基线就做优化，改完凭感觉说「快了」。
正确理解先记录基线（同场景、同设备、同画质），再改动，再复测；否则无法排除环境波动，也无法防止回归。
07

动手复现

前提：UE 5.x；先看趋势可用 PIE，但最终数值要在打包构建与目标硬件上取；固定相机、分辨率、画质档位与场景版本。

01选一个固定关卡与固定机位，记录 stat unit、stat fps 与 30 秒帧时间。
预期现象：得到一份可重复的基线，而不是一次性的截图。
02打开 ProfileGPU（或 Unreal Insights），找出占比最高的三个通道。
预期现象：能按通道排序，而不是只知道「GPU 高」。
03用 stat game / stat anim / stat physics 分别观察 CPU 侧热点。
预期现象：定位到具体系统（Tick、动画、物理、蓝图）。
04只改一个变量（例如关闭一层后处理），复测同场景。
预期现象：帧时间变化可量化，能验证假设而不是叠加改动。
05把该场景写进自动化或性能门槛，设定可接受的退化阈值。
预期现象：下一次改动若超阈值会被拦下，而不是上线前才发现。

步骤在编辑器内 5 步以内可复现；预期现象用来自检机制是否成立，不要求截图一致。

08

自测

1. 为什么平均 60fps 仍可能感觉卡？
解析：平均值被大量正常帧拉高，少数长帧（GC、流送、PSO 首次编译）造成明显卡顿。要看 1% low、帧时间曲线与尖峰出现的位置。
问题：性能回归没有基线，改动后才发现掉帧面试题：同屏敌人从 20 增至 200 时如何扩展 ARPG AI？
2. stat unit 显示 Game 22ms、Draw 12ms、GPU 14ms，应该先优化哪边？
解析：先看 Game 线程：它最高，且已经超过 16.7ms 预算。降分辨率对 Game 线程几乎无效，应该查 Tick、蓝图、动画、物理或 Actor 数量。
问题：无法判断瓶颈在 CPU 还是 GPU问题：Tick 与 Actor 遍历造成隐性 CPU 开销
3. 性能回归门槛为什么必须绑定固定场景与真机？
解析：不同场景/设备的负载不可比，编辑器与打包版本也不同。只有固定场景 + 目标设备 + 基线，数字才能反映真实退化；否则门槛会被噪声误伤或放过大问题。
