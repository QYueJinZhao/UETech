GC 与内存：卡在看不见的地方

UObject 不是普通 C++ 对象，它由 GC 管理。这一章讲清标记-清除在引用图上做什么、为什么会周期性卡顿，以及对象池、弱引用与内存峰值各自解决什么问题。

01

你会遇到什么问题

每半分钟卡一次，Profiler 里找不到具体函数

战斗打一会儿就顿一下，帧时间曲线出现规律性尖峰，但 CPU 采样里没有一个函数明显超标。你在关卡里来回走，内存持续上涨；退出再进又好一点。团队开始怀疑「引擎有问题」，但没人能说清 GC 什么时候触发、为什么这么久。

常见症状：
  • 帧时间周期性尖峰，间隔与玩法节奏相关
  • 内存曲线持续上升，怀疑泄漏但找不到引用链
  • 高频创建/销毁对象（子弹、飘字、临时数组）后更明显
  • 增加对象池后卡顿变少，但内存峰值反而更高
02

一句话直觉

GC 像餐厅打烊：先沿着「还有人用」的桌子走一遍做标记，再把没人用的桌子收掉；桌子越多、关系越乱，打烊越久。

UE 的 GC 从根集（GameInstance、World、Actor 等）出发，沿引用关系标记所有可达 UObject；没被标记的在清除阶段释放。对象越多、引用图越深，标记阶段越长。增量 GC 把一次打烊拆成几次做，单次停顿变短，但总工作量还在。

类比的边界：GC 只管理 UObject 及其引用；普通 C++ 内存（容器、裸指针）不由它回收，泄漏可能来自任何地方。

03

原理图解

GC 从根集出发遍历 UObject 引用图，给可达对象打标记；根集包括 GameInstance、World、PlayerController、被引用的 Actor 等。

标记结束后，未被标记的 UObject 在清除阶段被回收；被回收对象的引用需要被正确清理，否则会留下悬空或阻止回收。

对象数量与引用边数直接决定标记成本；临时对象（子弹、飘字、事件）频繁创建会让 GC 更频繁、更重。

增量 GC 把标记拆到多帧执行，降低单次停顿；GC 集群把一组对象合并遍历，减少重复访问与缓存不友好的跳转。

对象池减少分配/释放频率，但会长期占用内存；弱引用允许对象在无人使用时被回收，代价是每次访问都要检查有效性。

展开：再深一层的机制与边界
为什么「内存涨」不等于「泄漏」：加载的资产、缓存、对象池都会让内存上升，只要在预期范围内且可回收，就不是泄漏。真正的泄漏是对象已经不再被使用，却仍被某个引用链挂住，GC 无法回收。定位要靠引用链与快照对比，而不是只看总量。
04

关键代价

CPU 停顿
标记遍历与清除会造成尖峰；对象越多、图越深越明显。
内存
对象池与缓存降低分配频率，但抬高常驻峰值。
实现复杂度
弱引用、池化、增量 GC 都需要额外的生命周期管理。
稳定性
悬空引用、重复释放与泄漏会在长时间运行后集中爆发。
团队规范
谁创建、谁持有、何时释放必须统一，否则优化会被新代码抵消。

条形为相对量级（1–5 档），不对应具体毫秒、兆字节或人力数字。判断取舍时看「哪一项不可接受」，而不是追求每项都低。

06

常见误区

误区 1把所有分配都塞进对象池，认为这样就没有 GC 了。
正确理解池化只减少 UObject 的创建/销毁频率，不能消除 GC；池本身占内存，且池满/失效逻辑会引入新 bug。
误区 2把 UObject 当普通 C++ 对象，用裸指针长期持有。
正确理解UObject 由 GC 管理，裸指针不会被追踪，随时可能变成悬空；跨生命周期引用要用 UPROPERTY/弱引用并明确所有权。
误区 3内存上涨就归因于 GC 或引擎泄漏。
正确理解先区分资产缓存、对象池与真实泄漏；用引用链与快照对比定位，不能只凭总量曲线下结论。
07

动手复现

前提：UE 5.x；stat gc 只在部分构建可用，用 obj list / memreport 复核；对比时固定对象数量与生成节奏。

01在固定关卡执行 stat memory，记录物理内存、UObject 数量与 GC 次数。
预期现象：得到可比较的基线，而不是只看任务管理器。
02打开 GC 日志/统计（或 Insights），观察一次 GC 的标记耗时与回收对象数。
预期现象：能把尖峰与 GC 事件对应起来。
03连续生成/销毁一批临时 Actor（例如投射物），观察 GC 频率与帧时间。
预期现象：对象创建频率上升后，GC 更频繁或单次更重。
04把同一批对象改为对象池复用，复测内存与 GC。
预期现象：GC 次数下降，但常驻内存上升——验证取舍。
05用引用查看/快照对比，找出一个持续增长但未释放的对象链。
预期现象：能指出具体持有者，而不是笼统说「泄漏」。

步骤在编辑器内 5 步以内可复现；预期现象用来自检机制是否成立，不要求截图一致。

08

自测

1. GC 的标记阶段在做什么？为什么对象越多越慢？
解析：从根集沿引用图遍历所有可达 UObject 并打标记；对象数与引用边数越多，遍历工作量越大，缓存局部性也更差，所以标记时间上升。
方案：取舍：对象池 vs 依赖 GC问题：GC 长停顿造成周期性卡顿
2. 增量 GC 降低了单次停顿，为什么还可能影响帧率？
解析：它把一次标记拆到多帧，单次停顿变短，但总工作量仍在，且每帧都要分出一部分预算做 GC。如果步长设置不当，会持续占用帧时间。
方案：取舍：增量 GC vs 全量 GC面试题：如何定位 RTS 的 OOS，并设计回放与重连？
3. 对象池解决了什么问题，又引入了什么新问题？
解析：它减少高频创建/销毁带来的 GC 压力；但会长期占用内存，需要处理池容量、复用前重置、对象失效与引用清理，否则会出现状态残留或泄漏。
方案：增量 GC：把一次长停顿拆成多帧问题：对象池与 GC 的取舍错误
